## ADDED Requirements

### Requirement: Agent loads the full type registry at conversation start

Before generating any patch operation, the agent SHALL call `get_type_registry()` and load all `ResourceType` and `RelationshipType` records into its context. This call SHALL occur once at the start of each conversation session, not per-message.

#### Scenario: Type registry is loaded before first patch
- **WHEN** a user sends the first message in a conversation session
- **THEN** the agent calls `get_type_registry()` before generating any `patch_graph` operation

#### Scenario: Type registry is not re-fetched on every message
- **WHEN** a user sends a second message in the same session
- **THEN** the agent does not call `get_type_registry()` again unless the session context has been cleared

### Requirement: Agent resolves user language to registered types before patching

When a user describes a change involving a concept (e.g., "position", "team", "process"), the agent SHALL map that concept to a registered `ResourceType` name before generating a patch. If the concept maps clearly to a registered type, the agent SHALL use that type. If the concept is ambiguous or maps to multiple types, the agent SHALL ask for clarification before proceeding.

#### Scenario: Unambiguous concept maps to a registered type
- **WHEN** the user says "add a new COO position" and a `position` ResourceType is registered
- **THEN** the agent generates an `add_instance` op with `type: "position"` without asking for clarification

#### Scenario: Ambiguous concept prompts clarification
- **WHEN** the user says "add a new team" and both `Team` and `Group` ResourceTypes are registered with similar descriptions
- **THEN** the agent asks the user to clarify which type to use before generating any patch op

### Requirement: Agent uses NounCategory as a first-pass resolution filter

When searching for a matching ResourceType, the agent SHALL use the `category` field (`person`, `role`, `group`, `resource`) as a first-pass filter to narrow candidates before comparing names and descriptions. A user referring to a person SHALL only match ResourceTypes with `category: "person"`; a user referring to a role or position SHALL match `category: "role"`.

#### Scenario: Person reference resolves only to person-category types
- **WHEN** the user says "we hired Jordan" and only one `category: "person"` type exists
- **THEN** the agent creates an `add_instance` op using that person type without considering role or group types

### Requirement: Patch operations reference only registered type names

Every `type` field in a `patch_graph` `PatchOp` generated by the agent SHALL match a registered `ResourceType` or `RelationshipType` name exactly. The agent SHALL NOT invent type names that do not exist in the registry.

#### Scenario: Patch uses exact registered type name
- **WHEN** the agent generates an `add_instance` op for a concept mapped to the `Position` ResourceType
- **THEN** the `type` field in the op is `"Position"` (matching the registered name exactly, including case)

#### Scenario: Agent does not patch with invented type names
- **WHEN** a concept does not map to any registered type
- **THEN** the agent does NOT generate a `patch_graph` call with an invented type name; instead it either proposes a new type or asks for clarification

### Requirement: Agent resolves relationship types from directional constraints

When the user describes a relationship (e.g., "reports to", "owns", "is assigned to"), the agent SHALL identify the matching `RelationshipType` by considering both the name and the `from_type`/`to_type` constraints. If the endpoint types of the proposed link do not match the RelationshipType's declared constraints, the agent SHALL NOT generate that link operation.

#### Scenario: Relationship resolved with correct endpoint types
- **WHEN** the user says "Sam reports to Alex" and a `reports_to` RelationshipType with `from_type: "position"` and `to_type: "position"` is registered
- **THEN** the agent follows fills edges to resolve Sam and Alex to their positions, then generates `add_link` with type `reports_to` between those positions

#### Scenario: Mismatched endpoint types do not produce a patch
- **WHEN** the user describes a relationship whose endpoint types do not match any registered RelationshipType's constraints
- **THEN** the agent explains the mismatch and does not generate a `patch_graph` call
